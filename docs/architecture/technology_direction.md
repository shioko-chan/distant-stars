# Distant Stars：技术方向

## 决策

《Distant Stars》初步可玩版本继续采用 Web 技术栈，并将其视为 PC 正式版本的默认技术方向，不把当前实现当作之后必然废弃的临时 H5 原型。

当前不迁移 Unity、Godot 等通用游戏引擎。该决定不是永久排除游戏引擎；只有出现本文列出的硬性需求，并经过实际性能或生产流程验证后，才重新评估。

## 选择依据

游戏的主要复杂度来自长期模拟与信息呈现：

- 经济、人口、政治和科研系统的交互。
- 真实状态、确认情报和估计状态的分离。
- 航行、通信、命令传播和地方自主执行。
- 大量看板、列表、图表、历史记录和因果解释。
- 银河、恒星系和单星球的战略级三维可视化。

这些需求以数据模拟和复杂 UI 为主，不依赖角色控制、物理碰撞、战术战斗或大规模动画资产。DOM/CSS 更适合高密度策略界面，Three.js 已能承担现有星球表现和未来战略地图。迁移游戏引擎会要求重写现有渲染与界面，但不会直接解决核心模拟问题。

## 默认技术栈

- **TypeScript**：应用与模拟逻辑的主要语言。
- **Vite**：开发服务器和构建工具。
- **React**：看板、消息、命令和管理界面。
- **Three.js**：银河、恒星系和单星球三维表现。
- **Web Worker**：后台运行长期模拟，避免阻塞输入与渲染。
- **Vitest**：验证经济、政治、通信、命令和确定性回放。
- **结构化内容数据**：科技、政策、舰船、事件和平衡参数集中定义并校验。
- **Electron**：进入桌面发布阶段时用于 Windows、macOS 和 Linux 打包；初步可玩版本先保持浏览器可运行。

新增依赖前应检查现有能力和维护状态。只有依赖能够显著减少实现与维护复杂度时才引入。

## 架构边界

```text
应用
├─ simulation       确定性世界模拟
├─ content          科技、政策、舰船、事件与平衡数据
├─ presentation
│  ├─ galaxy        银河视图
│  ├─ system        恒星系视图
│  └─ planet        单星球视图
├─ ui               看板、消息、命令和管理界面
├─ persistence      存档、读取、版本与确定性回放
└─ workers          后台模拟入口
```

### 模拟核心

模拟核心不得依赖 DOM、React、Three.js 或具体页面生命周期。它必须能够在单元测试、Web Worker 和未来桌面后台进程中独立运行。

模拟核心负责：

- 统一帝国时间和事件排序。
- 世界真实状态。
- 航行与通信传播。
- 地方自主决策。
- 经济、人口、政治和科研结算。
- 确定性随机数与历史记录。

### 表现层

Three.js 只读取可展示状态并产生用户输入意图，不直接修改模拟对象。银河、恒星系和单星球视图共享选择、镜头和信息层级约定，但不共享彼此的渲染实现。

三维观景甲板由 `bridgeScene.ts` 独立持有渲染资源，本地 GLB 组成猫与舰桥设备，`bridgeMotion.ts` 提供可测试的角色和镜头时间线。开始过场结束后卸载舰桥并进入中控台；离开时释放动画、监听器、模型、纹理与后处理资源。开场不创建或修改权威模拟状态。

### UI 层

React UI 通过明确的查询结果展示玩家已知信息，不得绕过情报系统读取远方真实状态。玩家操作先形成命令或本地行政行为，再由模拟核心判断传播和执行。

### UI 模拟会话边界

应用根组件通过 src/ui/useSimulation.ts 持有唯一模拟会话，负责 Worker 生命周期、月步长推进、暂停和速度、自动保存、手动存读档及回放请求。该 hook 只在稳定的应用根组件调用，不在可切换的面板或地图中重复调用；根组件卸载会终止 Worker 并清理计时器。

页面负责选中对象、地图与部门切换、表单和新纪元确认，通过会话暴露的操作提交意图。日期组件只格式化和显示已确认时间与月内进度，不推进模拟。

观景甲板和中控台在同一根组件内切换，`useSimulation` 始终挂载；返回甲板时暂停推进，不重建世界。`useThemeMusic` 同样由根组件持有，两个界面的音乐控件共享播放、选曲和开关状态。

Worker 请求和响应统一定义于 src/workers/protocol.ts。界面交互与模拟规则可以分别修改；涉及命令字段或玩家可知信息结构时，需要同步更新协议双方。布局调整不应改变会话挂载位置或存档结构。

### 调试控制台

调试模式由启动地址中的 `debug=1` 显式启用，默认关闭。应用根组件把模式传入唯一模拟会话，Worker 在初始化时接收相同开关，并拒绝普通模式下的回放校验请求。历史面板只展示游戏报告，开发诊断集中在 `src/ui/DebugConsole.tsx`。

控制台采用原生 [`dialog.showModal()`](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/dialog)，支持键盘焦点、关闭按钮与 Esc；控制台内的 Esc 不传递给底层地图或经营面板。命令只支持 `help`、`replay`、`status`、`clear`，不执行任意 JavaScript。诊断信息读取既有玩家视图和响应耗时，不查询远方真实状态。

回放校验请求先暂停时间，校验在 Worker 内重建独立世界并比对，不替换活动状态。专用 `replay` 响应报告通过、不一致或异常及耗时，不走模拟致命错误通道，也不覆盖玩家通知。界面阻止重复校验；诊断日志由会话保存最近 200 条，关闭控制台仍保留，刷新清空，不进入游戏存档。

### 存档

存档保存权威模拟状态、传播中的消息与命令、确定性随机状态、内容版本和必要历史摘要。界面临时状态不应混入权威世界状态。

## 现有原型处理

保留并迁移仍符合设计的部分：

- 星球生成算法。
- 球面 LOD。
- 地图镜头与选择交互。
- 程序化建筑表现。
- 仍然有效的平衡数据。

移除并重写不适合扩展的部分：

- 单文件全局状态。
- 通过 HTML 字符串拼接维护的复杂界面。
- 渲染、输入和经济结算相互混合的逻辑。
- 只服务旧原型流程的路径。

不为旧结构增加兼容层。迁移按可运行的端到端增量进行；新路径接管功能后直接删除对应旧路径。

## 实施顺序

1. 建立 TypeScript、Vite 和测试环境，保持现有星球原型可运行。
2. 提取不依赖渲染的确定性模拟核心与时间系统。
3. 完成银河地图、舰船航行、通信和命令的最小闭环。
4. 建立 React 应用外壳与全局看板，逐步替换直接 DOM 操作。
5. 将现有星球算法与渲染迁入独立表现模块。
6. 加入 Worker、存档和性能监测。
7. 完成初步可玩版本后再接入桌面打包。

每一步结束时，产品必须能够启动并完成该阶段已有的完整流程。

## 重新评估游戏引擎的条件

只有出现下列至少一项经过验证的需求时，才重新评估技术方向：

- 必须正式支持主机平台。
- 微观观察成为包含大量角色、车辆和动画的核心模式。
- 战术战斗成为主体玩法。
- 团队生产严重依赖成熟的三维场景、动画和美术资产编辑管线。
- 性能分析证明目标规模无法通过 Worker、数据布局、LOD 或按需模拟解决。
- Web 图形或内存限制实际阻塞已确定的玩法，而不是仅存在理论风险。

重新评估时必须使用可运行场景和性能数据比较迁移成本，不能仅凭“游戏通常使用引擎”作为迁移理由。
